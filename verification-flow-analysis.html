Why every ticket stalls at AI Verification

A deep trace of the new evidence-based verification gate — how work is handed off, how it's tracked, and the specific design decisions that turn a one-step "prove it works" check into a 3-to-4-lap grind on every ticket. Built from live database evidence in epic 0aaf3207 · fready Personal Edition.

Generated 2026-07-19 · branch feature/epic-bc99b396-ai-verification-gate-evidence-based-review

TL;DR — the one-sentence cause

The gate is all-or-nothing and self-defeating: a demo can pass every executable step and still be rejected, and every rejection throws the ticket all the way back to in_progress — forcing a full re-implement → re-review → re-demo lap. Worst of all, the escape hatch the system tells agents to use (coverageRationale) is the exact thing that guarantees rejection. That's a catch-22, and it's why tickets bounce instead of finishing.

2 · The intended workflow (what should happen)

The status ladder is defined in core/workflow-steps.ts. On paper it's a clean one-way climb. Verification is the final gate before done.

The trouble is entirely in that red dashed edge. In the current design, verify-fail doesn't mean "try the demo again" — it means "you are no longer verified; go back to in_progress, throw away your demo, and re-earn your way here." Verification is the only gate in the ladder that can demote a ticket two full stages, and it fires often.

3 · How the handoff & tracking actually work

When a demo is generated (ai_review → ai_verification), the ticket is handed to a background verification worker. Four database tables track the whole lifecycle. Understanding them is key to seeing where state gets lost or stuck.

verification_jobs — the runner's work queue

One row per ticket. This is the durable lease/queue. Status moves queued → running → succeeded | failed | blocked | dead. A worker claims a job with a time-boxed lease (2–5 min), heartbeats to renew it, and settles it when the run finishes.

core/verification-queue.ts · core/verification-worker.ts

verification_runs — the sealed evidence ledger

One row per attempt (round 1, 2, 3…). Stores the HMAC-sealed manifest: every step verdict, boot log, git SHA, screenshots/API evidence hashes, and the certified boolean. This is the audit trail the epic table above was read from.

core/verification.ts (buildRun / persistRun)

demo_scripts — what to prove

The 3–7 step demo the runner executes. On every failure this gets wiped (completed_at=NULL, passed=NULL) and the workflow flag demo_generated is reset to 0 — which is what forces the agent to regenerate it from scratch.

core/verification-lifecycle.ts (updateDemoStepStatusesForRun)

ticket_workflow_state — the phase mirror

Tracks current_phase, review_iteration, findings_count/fixed. On a verification failure it's rewound to implementation, and a review_findings row is filed so the agent has something to "fix" — even when nothing was actually broken.

core/verification-lifecycle.ts (recordVerificationFindings)

Who executes the run

By default there is no resident poller. Execution happens through one-shot drain processes: when a demo is enqueued, Brain Dump spawns a detached brain-dump verify worker --drain that loads current on-disk code, runs the queue empty, and exits. This design (see shouldStartVerificationWorkerFromEnv) exists to avoid a server booting with a stale module graph — but it also means if that spawn silently fails, the job just sits queued forever until the next enqueue or a Brain Dump restart triggers a boot-drain. Startup reconciliation (reconcileVerificationTicketStates) exists precisely to mop up jobs that got orphaned this way — a tell that orphaning happens in practice.

4 · The bounce-back loop — why "one gate" costs four laps

Here's the mechanism that produces the sequences in §1. When a run is anything other than passed + certified, the lifecycle doesn't retry the demo. It runs returnTicketToImplementationAfterVerificationFailure(), which resets the ticket to the beginning of the working lane.

The cost multiplier

A "failure" at the gate is not a 30-second re-run of the demo. It is a full workflow lap: the agent must re-open the ticket, satisfy the review phase again, and regenerate the entire demo script from scratch (because demo_generated was reset to 0). With the observed 3–4 attempts per ticket, that's 3–4 complete laps where the intended design was one gate check.

core/verification-lifecycle.ts:525 · returnTicketToImplementationAfterVerificationFailure()

There are four different ways to "fail" the gate — and each is common

infra_error — the runner couldn't even boot/run the app failed — a real assertion failed uncertified — every step passed, but the run wasn't allowed to certify

summarizeStatus() is strict and ordered: any failed step ⇒ failed; otherwise any skipped step ⇒ uncertified; only an all-green run is passed. And certified = (status === "passed") — a single binary with no partial credit. In our epic, 2 of the 15 runs were infra_errors and 3 were uncertified — i.e. a third of all failures were not "the code is wrong," they were the gate refusing to certify working code.

5 · The coverageRationale catch-22 (the live stall on ticket 6)

This is the single most damaging flaw, and it's exactly what has ticket 6 stuck right now. Look at what happened: all 7 of ticket 6's demo steps executed and passed. The run was still thrown out.

Ticket 6's actual run manifest

step 1 · filepassedFile assertions passed.
step 2–7 · commandpassedCommand assertions passed.
step 0 · syntheticskipped "Verification run uncertified because the demo includes a non-certifiable coverageRationale."

Step 1 carried an honest note: "criterion:1 requires make lint and criterion:2 requires npx knip…" — the agent documented that two acceptance criteria for this Go project's dead-code sweep couldn't be fully proven by a single file assertion. That honesty is what torched the run.

Why it's a catch-22, not just a bug

The system gives the agent two contradictory orders in two different files:

Order A — the generate-demo gate demands it

core/review.ts:1063

"Demo steps must cover every acceptance criterion… Add covers references or an explicit coverageRationale that names each non-certifiable criterion id."

You cannot leave ai_review unless every criterion is covered. For a criterion that can't be automated, the sanctioned — and only — way through is a coverageRationale.

Order B — the verification runner punishes it

core/verification.ts:1605

"if any step has a coverageRationale → push a skipped verdict → the whole run is uncertified."

Uncertified ⇒ bounce to in_progress. The prompt even admits "rationale keeps the run uncertified" — the trap is documented, but the consequence (full bounce + eventual human block) is not survivable.

And the "self-heal" only fires once

The first uncertified run is "self-healed" back to implementation with a finding (returnUncertifiedRunToImplementation). But a second consecutive uncertified run blocks the ticket for a human (previousRunWasUncertified). So if the criterion genuinely can't be automated — which is the whole reason the rationale existed — the agent gets exactly one retry before the ticket is parked for manual intervention. That's what happened to ticket 2 (it survived by luck on the 3rd try) and what ticket 6 is walking into now.

6 · Ranked weak spots

W1

The coverageRationale contradiction

CRITICAL

Documented in §5. generate-demo forces a rationale for non-automatable criteria; the runner auto-uncertifies any rationale; uncertified auto-bounces; two bounces block for a human. Any ticket with an acceptance criterion that isn't cleanly expressible as a file/command/API/UI assertion is structurally unable to finish autonomously.

core/review.ts:1063 ↔ core/verification.ts:1605 ↔ verification-lifecycle.ts:649

W2

Every failure demotes two full stages instead of retrying the demo

CRITICAL

A flaky UI assertion, a slow boot, or a rationale doesn't get a cheap re-run — it wipes the demo, resets demo_generated=0, and sends the ticket to in_progress. The 3–4× run multiplier in §1 is entirely this. There is no "re-run the same demo" path and no exponential backoff on the demo itself; the only retry granularity is "redo the whole lane."

core/verification-lifecycle.ts:525

W3

App-boot fragility drives infra_errors on non-JS / cold-start apps

HIGH

Any demo with a UI or API step must boot the real app (vite dev auto-discovered, or a declared command) and drive Playwright. Cold Vite compiles routes on first hit; a splash overlay must detach; the boot must bind a chosen free port. Ticket 1 hit infra_error twice before a human ran a manual "Verification Startup Repair." discoverBootCommand assumes npm/vite by default, so non-JS stacks (this epic's target is Go) only work if they declare .brain-dump/verify.json — otherwise UI/API steps can't run at all. Two boot retries, then it blocks.

core/verification.ts:651 (discoverBootCommand) · :752 (bootApp) · :1077 (warmUpUiRoutes)

W4

The "3 consecutive failures" safety net rarely catches — or catches the wrong thing

HIGH

latestThreeFailedRunsShareStep only blocks when the last 3 runs are all status failed and share the same failing step order. But because every failure regenerates the demo from scratch, step orders shift between attempts, so the "same step" match often never happens — a ticket can bounce well past 3 times without ever being escalated. Meanwhile uncertified and infra_error runs aren't counted as failed at all, so a ticket alternating failed/uncertified never trips this net. The escalation logic and the demo-regeneration logic fight each other.

core/verification-lifecycle.ts:101

W5

The tripwire's manifest match is dangerously broad

MEDIUM

hasVerificationTripwireChange uncertifies any run whose changed files include a path containing the substring "manifest". That's meant to stop an agent editing Brain Dump's own verification code from self-certifying — but it matches innocent files in the target project too: public/manifest.json, site.webmanifest, app.manifest, manifest.ts. A frontend ticket that legitimately touches a web app manifest would be silently uncertified and bounced with a confusing "diff touches verification/manifest code" reason.

core/verification.ts:909

W6

Silent enqueue-drain spawn failures strand jobs

MEDIUM

With no resident poller by default, a job only runs if the detached drain process spawns successfully. Spawn failures are logged but never surfaced on the ticket — the job just stays queued. It's only rescued by the next enqueue or a Brain Dump restart's boot-drain + reconcileVerificationTicketStates. To a user this looks like a ticket sitting in ai_verification doing nothing, with no explanation.

core/verification-worker.ts:580 · core/verification-ops.ts:274

W7

Findings are manufactured for non-defects

MEDIUM

On an uncertified-but-all-passing run, a major review_finding is filed and findings_count is bumped so the agent has something to "fix." But nothing failed — the demo just wasn't certifiable. This pollutes the review ledger (ticket 7 shows 31 findings / 25 fixed) and trains the agent to churn on non-problems, inflating each lap.

core/verification-lifecycle.ts:429 (returnUncertifiedRunToImplementation)

7 · What to change

Ordered by impact-to-effort. The first two would, on their own, likely eliminate the stalling you're seeing.

R1 · Break the catch-22 — stop equating "not certifiable" with "must redo everything"

Decide one policy and make both gates agree on it:

  • Option A (recommended): a run where every executable step passed and the only "skips" are named coverageRationale criteria should resolve to a distinct terminal state — e.g. passed-with-caveats that completes the ticket but flags it for optional human spot-check. Don't bounce green work.
  • Option B: if you truly require executable proof, then generate-demo must reject coverageRationale up front (block leaving ai_review) instead of accepting it and ambushing the agent at verification. Fail fast, in the same phase, with the same information.

R2 · Make verify-fail retry the demo, not the ticket

Add an intermediate loop: keep the ticket in ai_verification and re-run the existing demo (or let the agent patch just the failing steps) for N cheap attempts before demoting to in_progress. Only fall back to a full lane reset when the failure is a genuine assertion regression, not a flake or a boot hiccup. This directly kills the 3–4× multiplier.

R3 · Separate infra_error from product failure in the retry budget

infra_error already has its own retry path, but boot fragility (W3) means it's hit too often. Warm the app once and reuse the boot across steps; give non-JS projects a clearer required declaration with an actionable error the moment a UI/API step is authored for a project with no discoverable boot, rather than at run time. Never let a boot flake file a "fix your code" finding.

R4 · Tighten the tripwire & fix the escalation net

Scope hasVerificationTripwireChange to the verifier's own repo (compare against Brain Dump's code root, not the target project's diff) and drop the bare "manifest" substring (W5). Rework latestThreeFailedRunsShareStep to count any non-passing outcome and to key on the failing criterion/assertion rather than the volatile step order (W4), so genuinely stuck tickets escalate predictably instead of bouncing forever.

R5 · Make stalls visible

Surface enqueue-drain spawn failures and stranded queued jobs on the ticket itself (W6), and stop filing fake review_findings for non-defects (W7). If a ticket is stuck, the reason should be one glance away in the UI — not buried in a detached process's stderr.

Expected effect

R1 alone unblocks ticket 6 immediately and prevents the whole class of "green work, rejected anyway" stalls (a third of the failures observed). R1+R2 together would have turned the observed 15 runs into roughly 6–8, and turned "every ticket stalls" into "verification is a quick final gate," which is what it was designed to be.

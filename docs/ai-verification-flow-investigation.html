Handoff Mechanics

The handoff to AI verification is not a single state update. It is a chain of writes and process launches. Any weak link can leave a ticket looking stuck.

Step Owner Durable write Failure mode
Generate demo Review tool Writes demo_scripts, moves ticket to ai_verification, enqueues verification_jobs. Open major/critical findings block this. Non-executable coverage may pass generation but later certifies as false.
Spawn drain CLI or MCP review command No state guarantee beyond the already queued job. If spawn fails, the job stays queued until boot recovery or manual drain.
Claim job Verification worker Sets job running, increments attempt, writes lease owner/expiry. Stale lease blocks other workers until expiry, unless recovery reclaims it.
Settle lifecycle settleVerificationLifecycle Writes run, evidence attachments, comments, ticket status, PRD state, job status. Pass goes to done. Failure loops to in_progress. Uncertified may loop once, then block. Infra errors retry or block.
Resume epic Epic continuation worker Enqueues one continuation job per epic after verification returns a ticket to implementation. A stale running continuation for the same epic can suppress the new continuation.

Weak Spots

Stale epic continuation lease can block the whole epic

epic_continuation_jobs has a unique row per epic. Enqueue only replaces the row when it is not running or the running lease has expired. In this epic, the row is running for a ticket that is already done, and the lease lasts 24 hours. That can prevent verification failures from automatically resuming the failed ticket.

Fix direction: during enqueue and claim, treat a running continuation as stale if its target ticket is no longer in_progress. Either replace it immediately or settle it as obsolete. Also add an operator command/status view for continuation jobs.

Ralph waits on ai_verification using only PRD state

The generated Ralph script pauses while every incomplete PRD item has status === "ai_verification". That is reasonable for short runner jobs, but dangerous when the PRD is stale, the drain did not spawn, the worker is paused, or a lease is stale.

Fix direction: bound the wait loop and call verification ops status from the loop. If queue depth is zero or the ticket left ai_verification in the database, refresh PRD and continue. If a queued/running job is stranded, stop with a targeted diagnostic.

ai_verification is marked active/workable even though agents cannot work it

Status metadata says ai_verification is active and workable, while the transition table only allows the runner to move it to done or back to in_progress. That mismatch leaks into UI and agent behavior.

Fix direction: split status metadata into agentWorkable and runnerOwned. Treat ai_verification as active but not implementation-workable.

coverageRationale is a trap for autonomous demo handoffs

Demo validation allows a step to name non-certifiable criteria with coverageRationale, but the runner will then mark the run uncertified. Ticket 6 hit exactly that path: all executable checks passed, but certification failed because criterion coverage was not executable.

Fix direction: for autonomous Ralph handoffs, fail generate-demo when coverageRationale is present, unless an explicit human-verification mode is selected. Alternatively, expand the safe command allowlist for project validation wrappers such as make when the project docs require them.

Verification drain spawn is best-effort after the durable handoff

The CLI and MCP tools enqueue the job, then try to spawn a detached one-shot drain. If spawn fails, the command still returns with the ticket in ai_verification and the job remains queued for boot or recovery. The current UI does not make this obvious at the epic level.

Fix direction: expose queue/drain state on the epic page and in Ralph's terminal loop. If drain spawning fails, add a visible ticket comment with the exact command to run: brain-dump verify worker --drain --pretty.

Fresh-eyes review failures are not durable jobs

Ticket 7 is stuck in review churn with open major findings and repeated reviewer failures/timeouts in progress logs. Review is still controlled by a shell subprocess, not a durable leased job with a first-class status.

Fix direction: give fresh-eyes review the same queue/lease/attempt model as verification, or at minimum write a durable review-run error row and block the ticket with a clear reason after repeated reviewer process failures.

Epic detail can make handoff look more complete than it is

The epic detail API maps a focused review run ticket from running to completed when the ticket is ai_verification or done. That is true for the review-run subtask, but easy to confuse with ticket completion.

Fix direction: label these as review completed or verification pending, and reserve completed for ticket done.

Stale CLI/MCP/schema versions still create weird handoffs

The progress logs show prior stale MCP behavior that moved tickets into old human_review paths or generated invalid demos. The code now has schema markers, but stale long-running tool processes remain a practical failure source.

Fix direction: every workflow command should print the workflow schema version, and Ralph should fail fast when the running MCP server's schema version is older than the local CLI/core schema.

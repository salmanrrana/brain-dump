Executive verdict

The epic is stuck in a distributed ownership failure.

No single component has an authoritative “I own the next move” record. Ticket status, verification job status, Ralph session state, the scoped PRD, and the epic-continuation lease can all disagree—and they currently do.

At the snapshot time there are zero tickets in ai_verification, so the present jam is not a verification queue backlog. Ticket 6 was returned to in_progress after an uncertified run but its repair continuation was not launched. Ticket 7 is in ai_review with two duplicate major findings open. Ticket 8 remains ready and cannot be selected while the earlier tickets are incomplete.

The biggest concrete bug is the epic-continuation record: it still says ticket 3 is running, holds a 24-hour lease until 2026-07-19T21:18:08.969Z, and points to a process that no longer exists. Because the table is unique per epic, ticket 6’s continuation enqueue silently preserved that stale record instead of replacing it.

The intended workflow

The design is reasonable on paper: the implementer and reviewer stop at a durable handoff; a separate runner owns evidence and the final verdict. The critical invariant is that ai_verification must mean “there is runnable or actively running verification work.”

The handoff is persisted in four places: tickets.status, ticket_workflow_state.current_phase, demo_scripts, and verification_jobs. The scoped plans/prd.json is a fifth projection. The implementation assumes these writes and later recovery actions stay coherent.

Where the real flow breaks

Ticket 6 shows the full failure path. Every executable verification step passed. The run was uncertified only because two acceptance criteria were represented by a coverageRationale. The lifecycle correctly returned the ticket to implementation, then failed to give that work to anyone.

The ticket demands

  • make lint
  • npx knip or ts-prune
  • make build && make test
  • Frontend tests, TypeScript, and production build

It is a contract mismatch between ticket requirements and Brain Dump’s verifier policy.

The weak spots, ranked by impact

These are workflow defects in Brain Dump itself. Some are already being addressed in the dirty worktree; none of the in-progress changes closes the entire epic-level loop.

Epic continuation leases are durable but not live

A continuation claims a 24-hour lease, then awaits the entire child Ralph script. There is no heartbeat and no child PID/session identity in the durable row. If the parent module is reloaded, the server restarts, or the promise is lost, the database says “running” for up to a day even when no process exists.

core/epic-continuation.ts:166–184, 197–242 · epic-continuation-adapter.ts:27–48

One stale row can veto every later repair in the epic

epic_continuation_jobs.epic_id is unique. The upsert only replaces the row if it is not running or its lease is expired. Ticket 6 therefore cannot install its own continuation while ticket 3’s orphan lease looks active. The enqueue function returns the old job and the caller ignores whether job.ticketId === requestedTicketId.

core/epic-continuation.ts:129–162 · verification-lifecycle.ts:525–559

The verifier policy contradicts project-specific acceptance criteria

Brain Dump tells agents to discover and run the target project’s actual validation commands, then limits demo command automation to seven binaries. fready’s required Go and dead-code commands are outside that set. The agent can either violate the ticket or add a rationale that makes certification impossible.

core/review.ts:340–386, 610–663 · live generate-demo errors at mcp-server.log:52847–52861

ai_verification previously mixed “runner owns it” with “runner gave up”

Terminal blocked/dead outcomes stayed in the same status as queued/running work. That makes “AI verification” ambiguous and lets the epic wait forever on work no runner will claim. The current uncommitted change correctly moves terminal outcomes to blocked in_progress, but deployed/live behavior must be reconciled and the surrounding continuation logic must also be repaired.

Fresh-eyes review has no durable deduplication or convergence rule

Ticket 7 has 31 findings in a single recorded review iteration. Twenty-seven are critical/major and 25 are fixed. The latest two open findings are duplicate descriptions of the same header-refresh state bug, submitted 30 seconds apart. There is no finding fingerprint, no “already open” guard, and no bounded repeated-finding escalation.

The outer loop’s circuit breaker is state-poor

It pauses only when every incomplete PRD entry is in ai_verification. It treats a lower incomplete count or a new high-water phase as progress, but a legitimate verification loopback to implementation is a regression in rank. Three otherwise successful iterations without a new high-water state stop the run—even when a repair is actively converging.

The epic screen groups tickets by status and names one “Active” ticket. It does not show the verification job, the continuation job, lease age, last runner activity, PRD drift, or which actor should move next. Repair plan

The goal is not another status rename. The workflow needs explicit ownership, convergent retries, and invariants that can be checked continuously.

P0.1

Replace the 24-hour continuation lease with a supervised process contract

Record child PID, process start time, session ID, launch generation, and heartbeat. Use a short renewable lease. If the child exits, settle immediately. If the parent dies, a supervisor should validate that the child/session still exists before renewing or reclaiming. A durable “running” row without a live process must become stale in minutes, not a day.

P0.2

Make continuation enqueue prove ownership transfer

After verification moves a ticket to implementation, the transaction must either create/replace a continuation for that exact ticket or set a visible blocked reason saying continuation launch failed. Return and assert the requested ticket ID. Never silently return an older epic job.

P0.3

Reconcile epic continuations continuously

Add a 10-second supervisor similar to the verification supervisor. Reconcile: running lease + no live process, job points to a done ticket, job points to a ticket different from the current repair target, expired launch profile, and active profile with no runnable owner. Provide operator status/requeue/dead commands for continuation jobs.

P0.4

Resolve the demo-command policy contradiction

Prefer a project-declared, reviewed verification manifest over a tiny global binary allowlist. Brain Dump should permit exact argv templates declared in .brain-dump/verify.json or project config, with fixed working directories, timeouts, environment scrubbing, and no shell expansion. This allows go, make, and project linters without opening arbitrary shell execution.

P0.5

Make ai_verification a strict ownership state

Allowed combinations should be finite: queued/running/retrying job + valid demo. Passed goes to done. Assertion failure and first uncertified run go to workable implementation with a repair owner. Exhausted/unsafe outcomes go to blocked implementation with an explicit action. No terminal job may coexist with ai_verification.

P1.1

Deduplicate and bound fresh-eyes findings

Fingerprint normalized category + file + line neighborhood + semantic description. Reopen or append evidence to an existing issue instead of inserting a duplicate. Track actual review rounds. After the same finding recurs twice after claimed fixes, escalate to a blocked review state with a human-readable convergence summary.

P1.2

Replace the no-progress counter with workflow-aware progress

Count evidence of convergence: finding fixed, failing step changed, new verification run, changed failure fingerprint, or owner heartbeat. Do not treat every loopback as regression. Conversely, do not reset the breaker merely because a status advanced and then immediately regressed to the same failure.

P1.3

Put orchestration state on the epic page

Show current owner, last heartbeat, current durable job, lease expiry/age, last run outcome, open blocking findings, PRD/DB drift, and the exact next automated or human action. Add a red “orphaned” state when no process owns a nonterminal ticket.

P1.4

Add transition invariants and alerts

Continuously assert: every AI-verification ticket has a valid demo and claimable/running job; no terminal verification job owns an AI-verification ticket; every autonomous repair ticket has a queued/running continuation or a live Ralph session; current epic ticket is not done; PRD projection matches DB. Alert after 60 seconds for broken handoffs and after 10 minutes for no owner heartbeat.

P2.1

Treat SQLite as source and PRD as a versioned projection

Add a projection revision or outbox record so writes cannot quietly diverge. Display drift in the UI and repair it from the database. Do not use grep counts over JSON as the primary orchestration signal.

P2.2

Accept unique ticket prefixes everywhere—or nowhere

Resolve an unambiguous prefix to a UUID in one core function and use it consistently in CLI/MCP adapters. Ambiguous prefixes should fail with candidates. This removes a large class of noisy autonomous retries.

P2.3

Make health summaries honest

A failed WAL check must make the overall health result degraded/error. MCP tool failures must be represented in telemetry error counts. Operator dashboards should never say “healthy” when a named sub-check is red.

How to recover this epic without creating another loop

These are the concrete next moves for the current fready epic. They are intentionally ordered; requeueing ticket 6 before fixing its demo contract will only reproduce the uncertified result.

  1. Repair or clear the orphaned epic-continuation ownership. Do this through a new operator-safe continuation control/reconciliation path, not ad hoc status guessing. The record must either be settled or replaced with ticket 6 and a live process.
  2. Make ticket 6 certifiable. Add trusted project-specific command execution for the exact required checks, then regenerate the demo without coverageRationale. All seven executable steps already passed; the missing proof is make lint and npx knip/equivalent.
  3. Resume ticket 7 once, with one owner. Merge the two duplicate open refresh-isolation findings into one durable issue. Fix shared refresh-result ownership between the header and grid, validate it, then run a single fresh-eyes pass.
  4. Generate ticket 7’s demo only after review convergence. Confirm zero open critical/major findings and ensure its Go/frontend commands can be expressed by the revised project-specific verifier contract.
  5. Start ticket 8 only after 6 and 7 are certified done. The hardening pass should include this entire incident as an acceptance scenario: failed verification must resume the same ticket, survive an app restart, and not block later epic tickets.

Do not diagnose this by the board column alone.

A ticket can leave ai_verification and still be stalled. The deciding question is: “Does a live actor or a claimable durable job own the next required transition?” For ticket 6, the answer is no.
